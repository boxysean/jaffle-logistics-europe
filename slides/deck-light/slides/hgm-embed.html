THE dbt MODEL, CONDENSED 
-- incident_reports_embed.sql
{{ config(materialized = 'incremental',
          unique_key   = 'chunk_id') }}

select
    chunk_id,
    chunk_text,
    content_hash,
    {{ dbt_context_engineering.embed('chunk_text') }}
        as embedding
from {{ ref('incident_reports_hashed') }}
-- only passages whose hash is new or changed
where {{ dbt_context_engineering.incremental_delta_predicate(
    'chunk_id', content_hash_column = 'content_hash') }}
Step three, embed. Each passage goes to an embedding model, here Databricks' gte-large-en, and comes back as 1,024 numbers. On the left, each passage is now a record with two new things: its content hash, a fingerprint of the text, and its embedding, the vector, first three numbers shown. Nobody reads these numbers; what matters is that passages about the same thing get numbers that sit close together. That is how search works: the question is embedded with the same model and the nearest passages win; for the Paris storm question IR-9001's first passage is nearest, at 0.779. On the right, the model: it is incremental, and the where clause only sends passages whose hash is new or changed, the same hash you see in each record, so unchanged text is never paid for twice. Only a change of embedding model re-embeds everything.
