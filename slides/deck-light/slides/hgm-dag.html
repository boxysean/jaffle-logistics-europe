That was one flow. Here are all seven. The incident reports flow we just followed is the amber one. Legal documents, CRM notes and call transcripts go through the same parse and chunk steps. Support tickets, dispatch notes and Slack threads skip chunking: a ticket or a dispatch note is already short enough to be one passage. Every source is embedded and classified the same way, with the same embedding model, because a corpus embedded by one model cannot be searched with another. Then all seven union into knowledge_base, one shape for all of them, 2,708 rows; dispatch notes are the biggest at 1,299. Search reads that one table. The search model, top right, is itself a dbt model: it embeds the question with the same embedding model as the corpus, compares it with every row by cosine similarity, and returns the ten nearest passages; it can filter first, on the classify label or the account, so the storm question only looks at weather_disruption rows. Seven sources, each a chain of small, ordinary dbt models. And you do not write them by hand: build this with skills. The package ships skills for a coding agent that set up, build the pipeline and wire the AI functions, which is the last slide of this part.
